# DataSense GPU candidate training

The current experiment compares four candidate approaches on the user's real
`dataset/combined_dataset.csv`. It does not call DemoDetector, TemplateProvider,
an LLM, SHAP, or LIME. No live traffic or automated mitigation is involved.

## Verified input and split

The CSV contains 685,671 rows, 94 columns, 400,672 benign rows and 284,999 attack
rows. `label4` is the fine-grained target: 84 classes including benign. The other
label columns, device names/MACs, timestamps and raw address/list fields are
excluded. The initial representation has 71 numeric network and sensor/log
features. It is therefore a multimodal DataSense experiment, not a network-only
deployment claim. The full source SHA256 and inspection are in
`artifacts/dataset_report.json` and `.md`.

The data contains overlapping aggregation windows with durations from 1 to 10
seconds. Preparation divides each class chronologically using the 70th and 85th
percentiles of unique window start times, sharing the boundaries across devices.
It excludes every window touching/crossing a boundary, then excludes feature
duplicates from later partitions. Exact duplicate protection uses hashes of the
selected float32 inputs; it does not establish absence of near duplicates.

This is **within-capture temporal evaluation**. Some attack types have only one
short capture, and benign/attack collection dates differ. It cannot establish
performance on unseen devices or independent captures. Timestamp removal alone
does not eliminate capture confounding. One class (`ddos_slowloris-port-8000`)
has no independent validation rows after exclusions; its validation recall is
unavailable. The per-class report shows support so that zero-support scores are
not mistaken for measured performance.

The full CSV was inspected, but this first resource-bounded search trains on a
proportional sample capped at 120,000 training rows and 30,000 validation rows.
Rare classes receive at least one sampled row where eligible. Another 30,000
test rows are saved and **not loaded by training or tuning**. No oversampling or
synthetic examples are added. All learned preprocessing fits training rows only.

## What each model actually is

| Candidate | Implementation | Device / adaptation |
|---|---|---|
| Random forest | XGBoost standalone forest; one boosting round, parallel trees | CUDA. Unlike sklearn RF, uses no-replacement subsampling and a second-order objective. |
| XGBoost | Gradient-boosted trees with histogram training | CUDA; validation macro F1 selects stopping iteration. |
| KAN | Original `Blealtan/efficient-kan` B-spline implementation | CUDA training; fixed spline grid, training-only imputation and scaling. |
| HEM adaptation | Original HEM binary and multiclass neural classes, source-equivalent closed-set vote, CUDA KNN | CUDA training/search; training-only imputation, scaling and PCA on CPU. KNN uses stratified 20,000- or 40,000-row training reference subsets according to the recorded configuration. |

HEM is a **DataSense adaptation**, not reproduction of published HEM performance.
Its original Kitsune feature representation is replaced by DataSense features;
the neighbor reference set is bounded for this laptop. The original repositories
are unchanged. No unknown-attack threshold or zero-day result is claimed.

HEM commit: `8513ad39c904dbe427727ee6f8470ee8a1ce8e0d`.
KAN commit: `7b6ce1c87f18c8bc90c208f6b494042344216b11` (MIT).
Official references: [XGBoost forests](https://xgboost.readthedocs.io/en/stable/tutorials/rf.html),
[XGBoost CUDA](https://xgboost.readthedocs.io/en/stable/gpu/index.html),

## Commands (PowerShell, project root)

For a presentation, load an already trained XGBoost checkpoint and classify a
real validation observation:

```powershell
.\.venv\Scripts\python.exe -m experiment.predict_trained --index 0
```

The output identifies the real backend, checkpoint, prediction and dataset label.
Change `--index` to another validation row from 0 through 29999. To use another
family, pass `--record artifacts/training/selected/kan.json` (or `hem.json` or
`random_forest.json`). This is saved-model inference, with no retraining, XAI or
LLM. The selected checkpoints are provisional validation leaders. Summary and
selection records are generated by `experiment.summarize_research`.

Use the existing environment, whose RTX 4050 CUDA execution was verified:

```powershell
.\.venv\Scripts\python.exe -m experiment.prepare_research
.\.venv\Scripts\python.exe -u -m experiment.train_candidates
.\.venv\Scripts\python.exe -u -m experiment.refine_candidates
.\.venv\Scripts\python.exe -m experiment.prepare_protocol_features
.\.venv\Scripts\python.exe -u -m experiment.protocol_ablation
.\.venv\Scripts\python.exe -m experiment.summarize_research
```

Preparation refuses to overwrite existing prepared arrays. Once preparation has
completed, run only the training command. Training resumes completed trials from
the same study directory and keeps every checkpoint in its unique run directory.
Do not edit prepared arrays or the recorded study definition to resume a run.
Resumption checks the exact configuration, seed, prepared path and manifest
digest, plus checkpoint existence. Legacy runs acquired their manifest digest
during an explicitly recorded post-run audit; originals and the audit trail are
retained under `artifacts/training/identity_audit_20260929/`. This is not a
pre-run cryptographic attestation of those older trials.

To create a separate later study, choose a new `--output` path. To prepare a
different data budget, choose a new preparation output and pass that directory
using the trainer's `--prepared` argument. A changed split or budget is a new
experiment, not a direct interchangeable score.

```powershell
.\.venv\Scripts\python.exe -m experiment.train_candidates --output artifacts/training/another_study
.\.venv\Scripts\python.exe -m pytest evaluation -v
```

The existing synthetic software demo still runs with `python run_demo.py` and
remains CPU-only and offline. It does not load these research checkpoints.

## Search and saved evidence

Each candidate has four configurations: unweighted baseline; the same parameters
with square-root inverse-frequency weights; changed parameters with those same
weights; and changed parameters with inverse-frequency weights. Class weights
are derived only from training counts, normalized by their training-sample mean,
then capped at 20. Both neural and tree backends use this definition.

The initial search uses seed 42. Its best configuration per family is repeated
with seeds 123 and 2025 on the same fixed split. These repetitions measure
training randomness, not uncertainty across independent captures. Configurations,
epoch/tree limits, purposes and seeds are in the study JSON. Neural early stopping
and XGBoost use unweighted validation macro F1. HEM saves both neural states
jointly at the best complete-ensemble validation epoch. Worse trials cannot
replace a better best-checkpoint pointer.

The second round changes one parameter at a time around each first-round leader,
then measures one paired change. Its five-trial blocks produce
`datasense_gpu_refinement/optimization_effects.md`. Increasing parameters is not
assumed to improve performance monotonically; a combination must be measured.
Selected settings are repeated across the same three seeds.

A separate feature experiment adds 99 observed protocol-presence features to the
71 numeric inputs (170 total), keeping the exact same row IDs and labels. Its
vocabulary is learned only from the training partition, with an unseen-protocol
indicator. No identifiers or target fields are added. This experiment is motivated
by observed TCP/UDP reconnaissance confusions and is reported separately under
`datasense_protocols_v1/`. Improved feature settings are repeated across seeds;
one additional boosted-tree capacity setting is tested.

The user target is at least one model reaching **99.97% fine-grained accuracy**.
The summary explicitly records whether this target was measured; it is not a
guarantee or permission to relax the split. `artifacts/training/RESULTS.md` and
`.json` summarize all distinct real-data trials and selected checkpoints.

The final data-volume check uses **480,405 eligible training rows** for the
leading XGBoost family. Validation and test IDs stay identical to the earlier
studies. This distinguishes effects of additional training observations from
changes in the evaluation population. The protocol vocabulary is refitted on
the enlarged training set only. Both unweighted and square-root-weighted
settings are measured, and the selected setting is repeated on three seeds.

```powershell
.\.venv\Scripts\python.exe -m experiment.prepare_research --output dataset/prepared/datasense_full_train --train-cap 1000000 --artifacts artifacts/training/full_data_inspection
.\.venv\Scripts\python.exe -m experiment.prepare_protocol_features --base dataset/prepared/datasense_full_train --output dataset/prepared/datasense_full_protocols
.\.venv\Scripts\python.exe -u -m experiment.scale_training
.\.venv\Scripts\python.exe -m experiment.summarize_research
```

The original 120,000-row training sample contains 24,064 all-zero numeric
observations spanning 63 labels. Direct array comparison verified conflicting
labels for identical numeric inputs. This limits fit on those training inputs;
it is not a measured test-set accuracy ceiling. The evidence is retained in
`artifacts/training/input_ambiguity.json`. Do not reinterpret the task as binary
classification or add scenario identifiers merely to meet an accuracy target.

Outputs under `artifacts/training/datasense_gpu_v1/`:

- `experiments.json` and `.csv`: all configurations, class weights, seed, data
  identity, measured validation metrics, timing and resource measurements.
- `comparison.md` and `.json`: per-trial comparison and repeated-seed summaries.
- `best/`: pointers and full records for the best measured trial per candidate.
- `runs/`: unique requests, logs, per-class metrics/confusion matrices, validation
  predictions, fitted preprocessing and model checkpoints.

GPU selection is checked; CPU fallback is an error. Neural peak allocated VRAM
is recorded directly. The additional periodic GPU measurement is device-wide
and includes other applications; sampled RAM/VRAM can miss short peaks. The
reload-and-predict time includes loading and is not a steady-state latency
benchmark. Every saved checkpoint is reloaded and checked against its original
predictions on a fixed validation slice.

Macro F1 includes all 84 declared classes (including the zero-support validation
class); inspect per-class support and false positives alongside the score.
Validation-selected leaders are provisional. Finalist configurations must be
frozen before the locked test is evaluated, and a decisive research winner needs
additional independent-capture evidence. Cleanup is postponed until selection;
retain the raw data, source provenance, splits, configurations and research results.
